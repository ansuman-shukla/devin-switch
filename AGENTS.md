# Verification and runtime constraints

- Run `make lint` and `make test`. Set `DS_TEST_NATIVE=/Applications/Devin.app/Contents/Resources/app/extensions/windsurf/devin/bin/devin` when running tests to also check compatibility with the installed CLI, using an isolated temporary database and no model requests.
- Typecheck the Mac UI with `swiftc -typecheck -parse-as-library -target arm64-apple-macos14.0 -framework SwiftUI -framework AppKit macos/DevinSwitch.swift macos/AccountViews.swift` on Apple Silicon.
- When building from inside a `ds` session, use `env -u XDG_DATA_HOME -u XDG_CONFIG_HOME -u XDG_CACHE_HOME -u XDG_STATE_HOME make app`. Otherwise uv's tool installation can end up inside the current account's private data directory instead of the stable user-level installation.
- Keep `--reinstall-package devin-switch` in the app install target: `uv tool install --force .` alone can reuse a cached wheel after Python source-only changes. Verify installed modules, not just the source-tree tests.
- A nested CLI can inherit `CHISEL_SESSION_DB`. Keep the native environment explicitly pinned to Switch's shared database; XDG isolation alone is insufficient.
- Runtime leases must survive into the native child via `pass_fds`. Release them by closing descriptors, not by explicitly unlocking a descriptor shared with a still-running child. Background tool processes can inherit these leases too: determine chat liveness using PID/start-time identity in `runtime/<run-id>.json`, not lease ownership alone. Keep the legacy run schema unchanged. A completed legacy run is inactive even if a background process retains its lock; never kill background servers automatically just to clear the session list.
- The saved default profile and the profile bound to an open CLI process are different concepts. Never silently change the latter when updating the default.
- Session tracking covers wrapper launches, not in-terminal `/new` or `/resume` changes. Do not label process liveness as agent activity or guess which newly created conversation belongs to a process.
- `!ds switch` is a one-command handoff: pick the next saved login with confirmed credits (`choose_best`: saved readings of any age only order the candidates, known-exhausted last; fresh checks run `CHECK_BATCH` at a time and the first confirmed login wins, because refreshing all 126 logins took ~35 s while the relay held the exhausted request), then close and resume automatically. Unknown/stale/exhausted usage is not eligible for automatic selection. Do not hold the global store lock during network refresh. Manage the `SessionEnd` hook in the isolated account's CLI config, preserving JSONC comments and existing hooks; never require or modify project configuration. Accept only the final `prompt_input_exit` receipt, never latest-history or the launch ID as a fallback. Keep receipts separate from launch metadata. Missing receipts and abnormal exits must not restart. A handoff updates the shared default only after the destination CLI process is created successfully, under the store lock; never select at queue time or revert it when that chat later closes. Normal `ds run --account` launches remain one-off overrides. Do not replay prompts, retarget other open processes, or drop sandbox/permission flags. Custom `--config` launches stay passthrough-only. Isolate inherited `DS_RUN_ID`, `DS_EXECUTABLE`, and `DS_FROZEN` in tests.
- Distinct saved chats may run and hand off independently in the same repository. Block duplicate known launch conversation IDs, not every chat in the repo; do not infer unknown IDs from latest history. Separate worktrees remain safest for concurrent edits.
- The terminal relay waits for the switch command to finish, sends separate Escape and Ctrl+D keys to its own child PTY, and cancels on timeout without force-killing. Once the final exit receipt arrives, stop sending keys and preserve the request while native shutdown finishes. Use bounded store-lock waits at restart boundaries. Test it with a real PTY and a fake CLI, including inherited background leases, slow shutdown, and terminal settings restoration. macOS may set the transient `PENDIN` flag on canonical-mode restoration; ignore only that kernel-managed flag when comparing terminal settings.
- Portable builds use `make dmg` and `make smoke-app`; audit wheels and source archives with `uv run --locked python scripts/check_dist.py` after `make build`. These checks use temporary state, not real accounts.
- Keep the PyInstaller runtime under `Contents/Resources/ds-runtime`, not `Contents/Helpers`: the latter makes macOS code signing interpret its data files as nested code. The frozen launcher must invoke its executable directly, without Python's `-m` arguments.
- Run `actionlint` when changing GitHub workflows. CI on pull requests and `main` runs only the essentials (one macOS 15 job, Python 3.11: lint, test, typecheck; superseded PR runs are cancelled). The Intel and Python 3.13 test runs, secret scan, package audit and DMG builds run only when `release.yml` calls CI with `release: true`. Release tags create drafts only after that full CI passes; Apple Developer ID signing and notarization are not configured.
- On macOS, `make test` also compiles and runs `tests/AppModelTests.swift` via `tests/test_macos.py`, using an injected offline bridge and isolated preferences. The row-label regression renders SwiftUI controls and uses on-device Vision text recognition to check visible captions, including disabled states, without changing their layout. Keep refresh timers owned by `AppModel`, not recreated SwiftUI views, and keep background polling separate from user-action busy state.
- Display names are cosmetic, stored atomically in each account's `display-name.json`. Keep the strict legacy `account.json` schema untouched so already-running older wrappers can still read it. Never rename account directories, selection pointers, leases, or session records when editing a display name; use the stable alias for every action.
- Global quota is an explicitly labeled sum of per-account credits, separately for daily and weekly windows, where 100 credits is one account's full allowance. Show the sum as a plain number against the capacity (100 per included account), e.g. "1,454 of 2,300 credits", plus the share left as a percentage ("63.2% left"); never render summed credits with a percent sign. Removing an account with quota left must lower the total; never average, which rises when a low account is removed. Absolute plan capacities are not available, so 100 credits means one full account regardless of plan. One weekly credit covers two daily credits: an account's global daily credits are min(daily left, 2 × weekly left), so daily is unchanged when it is at most the weekly reading and can never exceed its own reading or 100. Plans without a weekly window are not capped. Weekly credits and per-account meters keep their raw readings. Include exhausted accounts as zero, exclude stale/missing/signed-out readings from both total and capacity, and report coverage and not-applicable windows. Match the CLI's 120-second freshness limit and reject expired resets. Never add daily and weekly allowances together or call the result a shared balance.
- The Mac workspace supports a 640×520 minimum, a persistent 56-point collapsed sidebar rail, and bounded adjustable sidebar widths. Responsive grids must cap their column count at the number of items. Capture full scrollable layouts with `NSHostingView` in native tests: `ImageRenderer` alone does not render embedded native scroll views. Native mouse-event tests need a temporary, key, titled test window; hidden windows do not dispatch control clicks reliably. Keep these windows on the injected offline bridge and isolated preferences.
- Global quota represents currently usable allowances: exhaustion in either applicable window contributes zero to both daily and weekly totals, retaining the account in each applicable capacity. Validate both applicable windows before including an account; an unknown, invalid, or expired companion window must not imply availability. Not-applicable windows do not block the other allowance, and per-account meters retain their raw readings.
- `ds acp` is an experimental ACP v1 bridge, not an app-wide Desktop login switch. Keep one native child per loaded conversation; preserve bidirectional request IDs and user permission decisions. `/switch` and `/switch-status` are local controls, never model prompts. `ds switch --session ID` must target an exact live GUI launch; choose automatic accounts when the queued handoff becomes idle, without the global store lock held. Isolate inherited `DS_ACP_RUN_ID` in ordinary native launches and tests.
- GUI handoffs close native stdin without force-killing, load the exact conversation with transcript replay suppressed only for internal handoffs, and restore and verify reported session configuration before accepting prompts. Keep account bindings separate under `acp/`, leaving legacy run/account schemas unchanged. Reject host authentication overrides; registry output contains paths, never credentials, and does not install or edit Desktop configuration. Use subprocesses whose cleanup does not implicitly kill a slow native child. Tests cover inherited background pipes/leases and use fake accounts; native ACP compatibility checks remain credential-free and make no inference requests.
- Native ACP `session/new` can return an in-memory ID without persisting a session; local Switch control commands do not save it. Check exact shared-history availability before usage selection and again before stopping the source, ignoring only that source's own live run in duplicate checks. An unsaved or unavailable chat must stay open. `/switch-status` distinguishes process connection from saved history. Test this with the installed CLI in isolated, credential-free state and with deferred persistence in the fake CLI; never claim a conversation is saved solely because `session/new` returned an ID. Handoff and recovery errors should report safe stage names and RPC codes, not raw native errors.
- ACP mode/configuration changes and command revisions must reach the native child while a prompt is waiting for user input. Only explicitly allowed live controls (`LIVE_CONTROLS`, including Stop subagent `_cognition.ai/subagent/cancel`) and mid-turn prompts may bypass the prompt gate; pin them to that child and drain them before handoff or close so restored settings are current. The native advertises `cognition.ai/midTurnPrompts`, so Desktop sends steering `session/prompt`s during a turn: forward them to the running native (recorded for reload replay), not as a new gated turn. Local commands (`/switch`, `!ds switch`, blocked `/login` etc.) and prompts sent after `session/cancel` still wait for the turn. Keep permission and elicitation replies unchanged, including declines, cancellations, errors, edited-command metadata, and partial answers. Test delayed decisions and opposite approvals in concurrent chats; never auto-approve to resolve a blocked interaction.
- Saved ACP connections release their native process after 15 idle minutes, or on an exact-run `ds close --run ID` / Mac Close request. Gate release on saved history, no active requests/decisions/controls, and no queued switch. Use monotonic idle timing and separate `acp/lifecycle/` sidecars; older bridges and terminal launches must not offer the new Close action. Only deliberately suspended connections may reconnect automatically, after clean shutdown, with exact history, duplicate checks, the same account/context/sandbox and verified settings. Never replay a prompt, change the shared default, kill background servers, or automatically release chats that received a prompt but are unsaved or whose history is unreadable. Test real native unsaved IDs offline, slow/abnormal shutdown, delayed decisions, stale Close targets, and the native Mac button.
- Desktop windows each run their own `ds acp` bridge, and since Desktop 3.11 any window can open any saved chat. Loading a chat that another window's GUI run holds asks that run to release it when idle (lifecycle `close_requested`, the same gate as `ds close`), waits up to `HANDOVER_TIMEOUT`, then loads; a busy holder is left alone, its request reverted to `open`, and the load fails with a "busy in another Devin window" error. The released tab reconnects (taking the chat back the same way) on its next message. Terminal launches and older bridges without lifecycle sidecars are never asked and keep the duplicate-launch error. Concurrent loads of one chat in one bridge are serialized so Desktop's retries reuse the first agent.
- `session/list` is forwarded unchanged to a native ACP agent (the `initialize` probe, kept as the bridge's lister and closed after `LISTER_IDLE` seconds idle). Desktop 3.11 relies on the native's filters (`cwd`, `cognition.ai/sessionIds`, archived status), paging (`nextCursor`) and per-chat `_meta` (created time, space/tab IDs, lock state) to place chats in its sidebar; never rebuild the listing from history rows.
- Desktop's Customize page and composer `@` mentions send chat-less `_cognition.ai/*` requests (no `sessionId`: MCP list/install/remove/toggle/connect/listTools, skills/rules/hooks/subagents lists, and `_cognition.ai/scope_search` for `@mcpServer:`/`@rule:`/`@skill:`, whose categories come from the agent's `cognition.ai/mentionTypes`). `Bridge.ask_lister` forwards them unchanged to the same lister as `session/list`, outside the `listing` lock (an MCP OAuth connect can wait minutes for the browser), with no timeout. Desktop treats -32601/-32602 as "unsupported" and silently shows an empty page, so never reject these. The native answers them only when the client sent `cognition.ai/mcp` in `clientCapabilities._meta`, and writes user-scope changes through the account's `mcp_config.json` symlink into Switch's shared config. Notifications and requests that carry a `sessionId` keep the per-chat routing.
- An ACP reload closes a bridge whose native may keep shutting down (never force-killed), still holding the run lock. `acp_state.orphaned` recognizes such a run (controller lock file exists but no bridge holds it); `claim` waits up to `ORPHAN_TIMEOUT` for it to exit instead of failing with the duplicate-launch error, then reports that it is still shutting down.
- Switching a Desktop window between its agent surface and IDE mode makes the newly shown surface `session/load` the open chat again in the same bridge, and Desktop rebuilds that view from the load's replay. A native `session/load` during a running prompt ends the turn (`-32603 agent_channel_closed`, verified on 3000.11.216 offline), and a second native process refuses it (`-32015 session_locked`). So a reload while `chat.controls` is set (a prompt is in flight) never waits on the prompt gate and never reaches the native: `Bridge.replay` re-emits the Backend's record of what Desktop was sent since its latest native `session/new`/`session/load` (that load's replay, even when suppressed for a handoff, plus live updates, with prompts recorded as `user_message_chunk` because the native echoes them only in a load replay; only the newest update of each `BACKGROUND_UPDATES` kind), then returns that load's result with current settings. `session/resume` gets no replay. Idle reloads still go to the native. Records are JSON text, held only for open chats.
- Each bridge keeps one warm spare: a native started in the home folder and authenticated through its relay for the default login, with a `command` lease. `agent_for` gives it to the next `session/new`/`session/load`/restore on the same login (after `claim`, re-running the saved-chat checks via `Lease.attach(..., saved=True)`, which also rewrites the run's `project` and `kind` to the chat's), then starts a replacement in the background. The native serves sessions for any `cwd` regardless of its process folder. Other logins start cold; a spare for a former default is dropped. Spares close after `SPARE_IDLE` without use, and hold their login's shared account lock while alive. Tests that change fake-CLI environment switches after a bridge starts must wait for `bridge.filling` and `drop_spare()` first.
- Blank GUI chats (created by `session/new`, never forwarded a `session/prompt`, and absent from readable shared history) are also released after 15 idle minutes, never via manual Close. Native `session/load` rejects never-saved IDs (`session_not_found`) and `session/new` always assigns a new ID, so later prompts/controls/loads for that tab return a "start a new chat" error without starting a process or contacting the model.
- Idle timing counts GUI requests, native requests/responses, and conversation `session/update`s only. With Desktop capabilities (`cognition.ai/loadStats`) the native CLI emits `_cognition.ai/processMemory` telemetry every 60 s; extension notifications and metadata-only updates (commands/config/mode/session info/usage) must not reset the idle clock. Credential-free probes without Desktop `clientCapabilities` do not reproduce this. Test through `poll()` with a periodic fake emitter, not only direct `release_idle` calls.
- Switch-and-continue is the only exception to "no prompts after a handoff". The handoff sends exactly one literal `continue` (`handoff.CONTINUE_PROMPT`) and never replays the original prompt. Terminal: `!ds switch --continue` stores `continue: true` in the request, and `finish` appends `-- continue` only to that single resume. ACP: `/switch-continue` (and `!ds switch --continue`) forwards `continue` inside the same GUI prompt turn. Queued `ds switch --session` handoffs never send prompts, and `--continue` is rejected for them.
- Subagents live only in the native process, but the native saves each one's transcript in shared history (`subagent_heads` → its `message_nodes` chain). `subagents.py` records live `cognition.ai/subagent_started`/`_completed` events per conversation in `acp/subagents/<key>.json` (never during a load replay: `Backend.live` is set only after the load returns). When a replacement process opens a conversation (`go_live`), subagents an earlier process left running become interrupted; so do subagents that complete unsuccessfully with a quota error. Idle release refuses while a chat has running subagents. Interrupted subagents are offered to the user (`/resume-subagents`) or, when Switch already sends `continue` after a switch, appended to that same prompt: the resume text gives each one's original task and last saved steps and asks the parent to start fresh subagents that continue rather than redo. This is the only content Switch adds to `continue`; it is sent once and then forgotten.
- Auto-switch is a global setting in `$DS_HOME/settings.json` (`ds auto-switch on|off`, `/auto-switch`). It defaults on when the file is missing and fails closed when the file is invalid. ACP triggers only on typed native signals: a `session/prompt` error with code `-32011` and `cognition.ai/errorKind: resource_exhausted` and no `retryAfterSeconds` (rate limits carry one), or `_cognition.ai/agent_stopped` with cause `quota_exhausted`. It runs inside the prompt gate: drain controls before the handoff, honor `session/cancel` (no `continue` after a cancel), cap at `AUTO_SWITCH_LIMIT` switches per turn, and exclude logins already tried. On failure, re-raise the original quota error. Terminal detection of the rendered "Quota exhausted" text is only a hint. `queue_automatic` queues a handoff only after a fresh usage refresh confirms remaining allowance is exactly 0, the controller is still live, and no other request is pending. Automatic requests set `automatic: true` so the relay does not wait for a requester PID. The relay prints a "keep this chat open" notice as soon as the check starts and always reports why a confirmed-not-exhausted or unknown reading left the chat unchanged; exiting mid-check abandons it silently. `choose_best` reuses cached readings that `remaining_allowance` still accepts (≤120 s, unexpired resets), refreshes only the rest, and stops at the first confirmed 100% allowance (nothing can outrank it); if no early winner is signed in, it rescans every candidate. Test with the fake ACP quota styles (`FAKE_QUOTA_ACCOUNTS`/`FAKE_QUOTA_STYLE`) and a real PTY with styled, split alert output.
- Terminal quota detection is primarily typed OpenTelemetry. The installed CLI (verified on 3000.11.92, REPL and `-p`) exports an `api_error` log event with `error_kind: ResourceExhausted` and no `retry_after_ms` when quota rejects a request; this arrives even when nothing renders. `handoff.enable` adds `handoff.TELEMETRY` to the account's CLI config only when no `otel` block exists (an endpoint in user config is required to activate export; env alone is not). Its inert placeholder `logs_endpoint` (closed port 9, no exit delay measured) is overridden per terminal launch via `OTEL_EXPORTER_OTLP_LOGS_ENDPOINT` to an `otel.Receiver` on 127.0.0.1 with a random 32-hex path. Never redirect a user-owned or disabled `otel` block; prompt and tool content stay disabled. `Native.environment` drops an inherited receiver-shaped endpoint so nested launches cannot report into a parent chat. Typed signals bypass the 60 s text cooldown but are deduplicated within 10 s of a started check; the usage-confirmation gate is unchanged. The text watcher searches the whole stripped chunk (a single redraw can exceed its 512-byte carry-over tail). The CLI exports OTLP/HTTP protobuf only; `otel.log_records` is a dependency-free decoder, and `tests/otlp.py` encodes test payloads. Older running wrappers need one restart.
- Run GitHub CLI commands from Switch-managed sessions with `env -u XDG_DATA_HOME -u XDG_CONFIG_HOME -u XDG_CACHE_HOME -u XDG_STATE_HOME gh ...` so they use the existing user-level authentication rather than an account's isolated configuration directory.
- Native child environments pin `GH_CONFIG_DIR` to the incoming user-level GitHub CLI config before XDG isolation, honoring explicit overrides and ignoring inherited Switch account config roots. Keep it shared across ACP chats, handoffs, reconnects, and terminal launches; never copy or inspect GitHub credentials. Test resolution with temporary homes and real `gh config` commands, not real authentication. Older running bridges must restart to pick up this behavior.
- A destination native whose model catalog failed to load (cold `model_configs` cache plus slow network) returns a `select` option with `options: []`, silently falls back to a default model, and rejects `session/set_config_option` with `-32002` ("Model not found … Available models: "). It never reloads the catalog in that process, so in-process retries cannot help. Handoff/reconnect restore retries only this case by cleanly closing the agent and starting a fresh one (`CATALOG_ATTEMPTS`), suppressing replay after the first attempt. A `-32002` for an option whose list is non-empty is a genuine mismatch and fails without retrying. Reproduce credential-free paths with `FAKE_COLD_CATALOG_ACCOUNT`/`FAKE_COLD_CATALOG_STARTS`.
- MCP servers and their OAuth tokens belong to the user, not a Devin login. `Store.prepare` links every profile's `data/devin/mcp` to `shared/mcp` and `config/devin/mcp_config.json` to `shared/config/mcp_config.json`; only `credentials.toml` and `config.json` (with the managed hook) stay per account. Adoption runs for all profiles under `mcp.lock` so a token saved under another login is never stranded: tokens are newest-mtime-wins, swapped without a gap; server maps merge (newest wins per name; a lone file moves as-is to keep JSONC comments). Never delete superseded copies: rename them `*.superseded-<ns>`. The shared config must always exist (`{"mcpServers": {}}`): the native replaces a dangling symlink with a regular file, which the next prepare merges back. Another profile's unreadable file must not block a launch. Native `mcp add/remove/login/logout` write through these symlinks; verify with an offline stdio server, not real OAuth.
- The agent browser (`agent_browser.py`, `ds browser`) never attaches to the user's running Chrome: `--autoConnect` to it causes per-connection "Allow remote debugging" prompts, focus stealing, and the wrong profile. Each Chrome profile gets its own `browser/profiles/<slug>/user-data`, seeded by copying only `CLONED` items (cookies and site storage; no passwords, extensions or service-worker caches). Copies are never decrypted, and the source profile is only read. Chrome 136+ ignores debugging flags on the default data directory, and headless Chrome on macOS keeps the real keychain, so copied cookies decrypt. Chrome starts headless (`BackgroundOnly`: no window or focus change) with `--remote-debugging-port=0`; visible mode uses `open -g -n`. Reconnect by reading `DevToolsActivePort`.
- `ds browser mcp` is a per-chat stdio proxy around pinned `chrome-devtools-mcp` (`--autoConnect --userDataDir`). It injects `browser_profile`/`browser_close` and server instructions, binds the chat to one profile, restarts its child on a profile change (replaying `initialize`), and drops responses from stale children. The child gets temp directories as `--workspace` roots, because negotiated client roots otherwise make `/tmp` evidence files unwritable. Chats hold a shared `flock` lease. A daemonized supervisor closes Chrome `DS_BROWSER_GRACE` seconds after it can take the exclusive lock, holding it through shutdown. Chats release leases with `browser_close`, after `DS_BROWSER_IDLE` with no tool call in flight, or on exit. Visible-mode and refresh restarts require exclusivity. `ds browser install` writes the MCP entry to the shared and user-level configs and appends `mcp__browser__*` with the JSONC-preserving `handoff.extend_config`; `ds add` grants it once installed. Test with fake Chrome/MCP executables, never real profiles.
- macOS 27 App Data Protection (`com.apple.macl` on `~/Library/Application Support/Google/Chrome`, rules in `sandboxd`/XProtect) returns `EPERM` to every process except Chrome's own Team ID and apps with Full Disk Access. macOS attributes agent MCP servers to Devin.app (GUI) or the terminal, not Devin Switch. `browser.profiles()` raises `ChromeBlocked`; `agent_browser.profiles(store)` then falls back to copies under `browser/profiles/*/source.json` that have `user-data` (`source.json` saves `name`; older copies resolve by directory/email). Only `clone` (first copy or refresh) needs Chrome's folder and fails with `ChromeBlocked` before touching the existing copy. Launching Chrome on a copy works without access. Simulate the block in tests with `chmod 0` on the fake Chrome folder.
- GUI quota relay (`relay.py`): the native binds credentials per session/subagent at creation, never retries quota errors, and keeps regular subagents only in memory (a restart or an in-process `session/load` wipes them; only the sidekick persists in `subagent_heads`). Each chat Backend with a TOML `windsurf_api_key`/`api_server_url` login starts a loopback relay before `authenticate {methodId: "windsurf-api-key", _meta: {api_key, api_server_url: <relay>}}` (what Desktop sends); the native never writes this to `credentials.toml`. A failed host login (e.g. offline) closes the relay and leaves the native on saved credentials. The relay accepts only requests carrying the issued key (header or body), swaps it for the active login's same-length key in header and body (inside gzip `Content-Encoding` bodies and gzip-compressed Connect envelopes too: the native gzips its chat streams and the server bills the key inside the request, so a header-only swap keeps charging the exhausted login), and replays a request whose first Connect frame is an end-stream error matching "(daily|weekly) usage quota has been exhausted" (sent as `failed_precondition`). Rotation obeys the global auto-switch toggle, uses `choose_best` excluding tried logins (at most `ROTATION_LIMIT`), runs once under a lock for concurrent failures, then moves the chat binding, run record (`Lease.adopt`, schema unchanged) and shared default. Anything else passes through unchanged so restart-based auto-switch remains the fallback. Never log keys. Test with `tests/fake_upstream.py`, the fake ACP `infer`/`subagents` prompts (`FAKE_SUBAGENT_GATE`), and the credential-free installed-CLI checks; reproduce real quota errors with an exhausted login and a quota-counted model (`swe-1-6-fast` is not counted). Terminal `ds run` launches are not relayed.
- When a quota error still reaches a relayed GUI agent (relay rotation limit, or a form the relay does not replay), `prompt_turn` first recovers in place: `Relay.recover` keeps the relay's active login if the relay already moved past every login exhausted in the last `EXHAUSTED_MEMORY` seconds, or rotates to the next login with credits, then sends `continue` to the same native so in-memory subagents survive. Only if that fails does it restart via `switch`. Notes name the logins that ran out, captured before the relay can move. The relay appends key-free events (endpoint names, statuses, aliases) to `$DS_HOME/logs/relay.log`, rolled over at 1 MB.
- Desktop panels (`ds panels install`, `panels.py`, `desktop_extension/`) are a plain-JavaScript VS Code extension with no npm dependencies, packaged as a VSIX by Python with `ds.json` holding the installing `ds` argv, and installed with Desktop's `bin/devin-desktop --install-extension --force`. Detect installation from `~/.devin/extensions/extensions.json` (`DS_DESKTOP_EXTENSIONS` in tests), never from a settings flag. The frozen app bundles the folder via `--add-data`.
- Whiteboards: the extension is a whiteboard-mcp panel host (`whiteboard.js`): it reads `<WHITEBOARD_HOME>/daemon.json` + `token`, connects to `/ws/host`, says hello with `hostId: String(process.pid)` plus its workspace folders and focus, opens the board when the daemon sends `show`, and reconnects when the daemon restarts (the daemon idles out). The extension host's pid is the window identity: Desktop starts every chat's agent (and so its whiteboard-mcp) with `WINDSURF_EXT_HOST_PID` = that pid, and the daemon routes a board only to the matching window (or one showing its folder), never to an unrelated one. Each board gets its own tab (`canvas.js`, keyed by canvas id); showing a board reveals its tab and must never retarget another board's tab, or one chat's drawing hides another's. Showing must not depend on launch-time environment: an earlier design (`ds canvas show`, `WHITEBOARD_OPEN`, request files) broke for chats started before an update and for chats not launched through Switch. Do not use `devin://` URIs either: untrusted extension URI handlers trigger a confirmation prompt and route to the last active window. Switch's only whiteboard role is `ds chat id` (live GUI run from `DS_ACP_RUN_ID` → conversation id; fails outside one), exposed to native children as `WHITEBOARD_CHAT_COMMAND` via `setdefault` so a board follows its conversation across handoffs.
- The Agent Browser panel talks to `ds browser view` (JSON lines on stdio). It holds a shared lease only while attached and releases it on `detach` or stdin EOF, exactly like a chat; never take the exclusive lock or change headed mode from the panel. CDP runs in the extension host with Node's built-in WebSocket (Desktop's extension host is Node 24): flattened sessions, `Page.startScreencast` with acks, an initial `Page.captureScreenshot` (headless Chrome only paints on change), and input via `Input.dispatch*`. Frames from a previous session must be dropped. Follow mode switches to new or navigating tabs until the human picks a tab.
- Extension tests: `tests/desktop_extension/*.test.js` (node:test, wrapped by pytest; includes a real headless Chrome test when Chrome is installed). `DS_TEST_DESKTOP=1` (needs `whiteboard-mcp` on PATH) runs a real whiteboard daemon and an isolated Desktop window with `--extensionDevelopmentPath`/`--extensionTestsPath` (folder with `index.js`, which runs inside the extension host, so its `process.pid` is the window's `hostId`); keep `--user-data-dir` under /tmp because Electron's IPC socket path must stay below 104 characters, and strip inherited `VSCODE_*`/`ELECTRON_*` variables.
- `initialize` keeps Switch's own `sessionCapabilities` (`list`, `resume`, `close`) and passes through only the native's `additionalDirectories` (without it Desktop drops a multi-root window's extra folders from `session/new`). Native `delete` and `close._meta.cognition.ai/force` stay hidden: Desktop would delete chats the bridge still holds, or force open a chat another window is busy with, which the cross-window handover never does.
- GUI chats follow the native's folder rules: native 3000.11.216 loads a saved chat with any absolute `cwd` (even a deleted folder or a different one; history keeps the original project) and `session/new` accepts a missing `cwd` (Desktop's worktree prewarm and space migration send them). So the bridge requires only an absolute path, uses `sessions.available` (in history, not held by another launch) instead of `resumable`, starts natives in the home folder when the project is gone, and handoff/close checks require only the saved history row. Terminal launches keep `resumable` and its folder checks, because the CLI runs inside that folder.
- Desktop sends a window's editor and terminal context as chat-less `_cognition.ai/document/*`, `workspace/*` and `terminal/*` notifications (the built-in agent gets them in its single per-window native; native 3000.11.216 accepts them chat-less). The bridge broadcasts only these three namespaces (`EDITOR_CONTEXT`) to all its started natives; other chat-less notifications (e.g. a stray `mcp/removeServer`) stay rejected, because Customize actions run only as lister requests without counting it as activity (`Backend.notify_editor`), so it never keeps an idle chat open. It keeps the replayable editor state (open documents minus closed ones, latest focus, latest revision per repository uri, in last-sent order) and writes it to each new native right after `initialize`, before any newer context. `didChangeDirty` (only a uri, unclear toggle semantics), file-change events and terminal events are not replayed.
- Desktop shows "Devin Switch is starting…" until the bridge answers `initialize`, which starts the listing native. That native (`chat=False`) needs no verified login, so its `Lease` skips `require_login` (`verify_login=self.chat`). The check (`devin auth status`, a network call, up to 10 s on a slow network, cached only in memory per process) still runs for the warm spare and every chat native, in the background or when a chat opens.
